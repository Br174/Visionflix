PURPOSE
Compact verified local MotorLab fallback bundle for registered projects. Central Br174/Chatgpt remains authoritative whenever reachable.

LOCAL ACTIVATION
When project context is recognized and this bundle is VERIFIED in .motorlab/MOTORLAB_SYNC_STATE.txt, MotorLab may activate immediately from local satellite while checking central release at the first safe boundary.

VISIBLE STARTUP
Normal startup message is exactly:
"⚙️ MotorLab attivo"

CHANGE COMPATIBILITY GUARD
Before any write-capable MotorLab/project change:
- inspect current implementation/configuration/protected behavior;
- identify existing mechanisms touching the same responsibility and native-engine ownership;
- check conflicts, semantic overlaps, duplicate responsibility, precedence ambiguity, blast radius, backward compatibility and regression risk;
- classify CLEAR / COMPLEMENTARY / MERGE_REQUIRED / PRECEDENCE_REQUIRED / CONFLICT / OBSOLETE_PATH / BLOCKED_UNSAFE;
- merge/extend existing mechanism or define explicit precedence/supersession before writing;
- do not write while an unsafe unresolved conflict remains.
Atomic changes may use a concise check, but never skip it.

WATCHDOG COORDINATION
Watchdog is the single coordinator for progress-health detection and anti-stall intervention.
- Foreground Stall Guard owns prevention/chunking/durable handoff;
- Resume Recovery owns checkpoint continuation, manual-lightning Rapid Salvage Checkpoint and monotonic recovery-floor reconstruction;
- Background Execution owns persistent jobs;
- Progress Reporting owns user-visible operational status and verified percentages;
- Change Compatibility Guard owns pre-change compatibility.
Do not run competing recovery paths for the same event.

PREVENTIVE HEALTH CHECK
During substantial work, when control/status evidence exists, perform lightweight progress-health checks at meaningful boundaries when progress appears unclear, repetitive or unusually slow.
A visible preventive check may say:
⚡ Controllo MotorLab — verifico che questa fase stia producendo progresso reale.
Do not interrupt healthy work or fabricate a stall.

TWO-STRIKE NO-PROGRESS RULE
If the same write/retry/recovery strategy is attempted twice without material progress or new evidence, a third materially identical attempt is prohibited.
First distinguish healthy external waiting from failure. If not healthy waiting, switch strategy, diagnose, narrow the substep or safe-stop.
Repeated read-only status probes of a legitimately running job do not automatically count as failed strategy attempts.

MANUAL LIGHTNING SAVE-THEN-RESUME
When Bruno sends only or primarily `⚡`, treat it as a high-priority SAVE-THEN-RESUME request at the first available execution cycle:
- identify active/pending operation and previous checkpoint;
- BEFORE any recovery/retry/new write, create or refresh a lightweight MANUAL_LIGHTNING_SALVAGE checkpoint with the freshest recoverable material state currently available;
- capture when available: current phase, latest completed material step, exact next safe step, pending verification, verified percentage, latest user-visible verified MotorLab percentage, progress fingerprint, repo/ref, provider/job status/id, artifact/result identity and writer lock scope;
- keep salvage bounded and fast: use current known state first and only the smallest targeted read/status probe needed; never do a full repository copy, exhaustive traversal, full log archive or rebuild merely to create the salvage checkpoint;
- preserve completed work, percentage and single-writer ownership;
- reconstruct the MONOTONIC RECOVERY FLOOR before choosing a continuation point;
- after salvage, Watchdog classifies health and Resume Recovery continues from the smallest safe pending step compatible with the floor;
- if healthy external work is still running, do not duplicate/cancel it;
- if no pending operation exists, say so rather than inventing one.

The salvage checkpoint is state preservation, not a second health coordinator and not a retry. It does not by itself increase verified progress.
Automatic recovery remains mandatory and does not depend on `⚡`.
If ChatGPT is fully suspended and does not accept/deliver the message, `⚡` cannot create an execution cycle by itself.
The command cannot retroactively capture hidden model reasoning that was interrupted before the new cycle; it preserves the freshest observable/recoverable material state available when the cycle begins and reconciles real external state before continuing.

MONOTONIC RECOVERY FLOOR
For the same logical operation and compatible progress scale:
- reconcile persisted checkpoint/ledger progress, latest user-visible verified MotorLab progress, verified micro-milestones and current repo/provider/job/artifact evidence;
- use the highest coherent verified value as recovery_floor_percent;
- a stale lower checkpoint MUST NOT reduce recovery below newer coherent verified progress;
- normal recovery may repeat or increase the floor but must not silently go below it;
- lower recovery is allowed only when material evidence proves previous progress was invalidated or a newly approved operation uses a different progress scale;
- any such invalidation must be stated visibly with the reason/evidence.

Not valid reasons to lower the floor:
- interrupted chat/model turn;
- failed/queued `⚡` send;
- missing newer checkpoint;
- older persisted checkpoint;
- elapsed time;
- temporary conversation-load failure.

Example: same operation at verified 93% with an older 20% checkpoint resumes at a 93% recovery floor while current job/ref state is reconciled. It does not silently show 20%.

FOREGROUND STALL GUARD
Before substantial work classify FOREGROUND_SHORT / FOREGROUND_RISK / BACKGROUNDABLE / USER_BLOCKING.
For risky/backgroundable phases checkpoint first, record next safe step and prefer a real persistent executor when available; otherwise use bounded recoverable segments.
If the same foreground strategy produces no progress twice, route to Watchdog before a third identical attempt.
ChatGPT UI "still processing" is not MotorLab progress/heartbeat.

PROGRESS REPORTING
For substantial work provide denser live-like operational visibility when the interface permits, normally after roughly 1-2 meaningful operations or material phase/status change.
Show observable actions/results/current state/next action; do not expose hidden chain-of-thought.
Percentages remain verified completion only and may repeat with useful new status.
For the same operation, verified progress is monotonic across recovery unless material invalidation evidence is explicitly reported.
Preventive/recovery lightning updates should include the current recovery floor/verified percentage when available.
For manual `⚡`, salvage + recovery may be reported in one concise message to avoid needless delay/spam.

WATCHDOG LEVELS
- ⚡ verify / preventive progress-health check;
- ⚡⚡ safe continuation / changed strategy;
- ⚡⚡⚡ checkpoint recovery;
- ⚡⚡⚡⚡ safe stop when continuation would be unsafe.
Visible Watchdog output always includes explanation; the user input `⚡` may be bare as the manual command.

RESUME RECOVERY
After every tool/provider/build/API/GitHub response, if the approved task is incomplete and execution control remains available, continue to the next safe action in the same turn. If the host/model interrupts execution, resume at the first later available execution cycle from the last verified checkpoint/pending action. Do not require Bruno to say "continua" for a known safe pending action.

CHECKPOINT
For substantial operations, preserve enough state to resume deterministically: operation/project, source ref/SHA, phase, completed milestone, exact next safe step, last verified progress, relevant job/artifact identifiers and recovery state when available.

SINGLE WRITER
Only one write-capable operation may act on the same project/repository/ref/resource scope at a time. Read-only diagnostics may run independently when safe.

NATIVE ENGINE COEXISTENCE
MotorLab is control-plane/orchestration infrastructure. It must not replace, absorb, disable or rewrite the project's native/domain engines merely because MotorLab is active.

LIFECYCLE AND PROTECTED STATE
Respect the project's current canonical lifecycle and protected source rules. MotorLab satellite installation alone never authorizes direct modification of MADRE, package/signing identity, release semantics, protected UI or other project-specific protected behavior.

CENTRAL SYNC
At a safe boundary, compare local RELEASE against MOTORLAB_RELEASE_MANIFEST_V1.txt in Br174/Chatgpt. If central is newer, follow MOTORLAB_SATELLITE_SYNC_V1.txt. Never switch MotorLab release midway through an active operation.

FALLBACK
If central MotorLab state cannot be reached, a VERIFIED local bundle remains usable. Preserve the current project and report fallback when it affects the work. Do not claim a newer version than the local verified release.

PLATFORM LIMIT
A repository cannot create a new assistant turn while ChatGPT/the host exposes no execution cycle. Foreground Stall Guard reduces exposure to that state; Resume Recovery continues at the first later available cycle. Neither is an autonomous wake-up mechanism for a completely suspended host.

NO RUNTIME COUPLING
This bundle is development/orchestration metadata. Its presence must not intentionally increase APK/PWA runtime dependencies or change app behavior by itself.
